# OpenSpec graph backend (FalkorDB)

An optional variant of the experimental `/opsx` workflow skills that stores
OpenSpec change artifacts in **FalkorDB** instead of writing markdown files
under `openspec/`. This document is the shared contract between the renderer
module (`.zcode/scripts/openspec-graph-render.mjs`) and the adapted skills.

## Running it yourself

Everything in git works against your own FalkorDB instance - no credentials or
instance details are baked in:

- a reachable FalkorDB server; the renderer reads `FALKORDB_HOST`,
  `FALKORDB_PORT`, and `FALKORDB_GRAPH` (defaults `localhost` / `6379` /
  `openspec`)
- agents reach the graph through a FalkorDB MCP server (`query_graph` with a
  `params` object); humans read the markdown projection through the renderer
- one graph (default name `openspec`) holds **every project**, keyed by the
  `project` property on `Proposal` and `Spec` nodes (the repository root path;
  `projectName` is its basename for display)

## What is tracked vs. local

| In git | Local only (gitignored) |
| --- | --- |

| `.zcode/scripts/openspec-graph-render.mjs` | `.zcode/export/` (renderer output), `.zcode/plans/` |
| | `.bob/` skill/command mirrors (repo convention ignores tool dirs) |
| | `.roo/` (stock, regenerated by `openspec update`) |

## Regeneration warning

The adapted skills under `.zcode/` and `.bob/` are generated files (they carry
`generatedBy` metadata) that were hand-diverted to the graph backend. A stock
`openspec` binary overwrites them on the next `openspec update`. The
`preserve-customized-skills` branch patches update (see
`src/core/update-customization.ts`) to preserve any managed artifact whose
frontmatter `metadata:` block carries a key the generator never emits - these
files carry `metadata.backend: falkordb` - and to buffer the fresh stock
content under `openspec/update-buffer/` instead of overwriting. Port worthwhile
upstream changes from the buffer into the customized file, then delete the
buffer.

## Schema

Change cluster (one per change):

```
(:Proposal {id, name, title, project, projectName, status, schema,
            why, whatChanges, newCapabilities, modifiedCapabilities, impact,
            skipSpecs, retireCapabilities, specsSynced,
            createdAt, updatedAt, archivedAt, archiveName})
   │
   ├─[:REQUIRES]──────────► (:Architecture {content, createdAt, updatedAt})
   │                            │
   │                            └─[:DECOMPOSES_INTO]──► (:Task {
   │                                                       id, proposalId, groupIndex,
   │                                                       group, index, description,
   │                                                       status, completedAt
   │                                                    })
   │
   └─[:SPECIFIES]─────────► (:SpecDelta {capability, purpose})
                               │
                               └─[:HAS_REQUIREMENT]──► (:Requirement {
                                                          name, text, operation,
                                                          fromName
                                                        })
                                     │
                                     └─[:HAS_SCENARIO]──► (:Scenario {
                                                             name, given, `when`,
                                                             outcome, ands
                                                          })
```

Main specs (after sync/archive):

```
(:Spec {project, capability, purpose})
   └─[:HAS_REQUIREMENT]──► (:Requirement {name, text})
                             └─[:HAS_SCENARIO]──► (:Scenario {name, given, `when`, outcome, ands})
```

Field notes:

- `Proposal.id` = `<projectName>/<name>`; `Task.id` = `<proposalId>/<groupIndex>.<index>`.
  These mirror tasks.md numbering (`2.1` = group 2, task 1).
- `Proposal.status` lifecycle: `planning` → `implementing` (first task flipped)
  → `complete` (all tasks completed) → `archived`.
- `Proposal` markdown-string properties (`why`, `whatChanges`, `newCapabilities`,
  `modifiedCapabilities`, `impact`) hold the proposal.md section bodies verbatim.
- `Architecture.content` holds the full design.md body (after the `# Design` heading).
- Delta `Requirement.operation` ∈ `ADDED` | `MODIFIED` | `REMOVED` | `RENAMED`;
  `fromName` carries the old name for RENAMED. Delta requirement nodes are
  **records** - sync reads them but never rewrites or deletes them.
- Scenario properties avoid the reserved word `then`: `given` (optional),
  `when`, `outcome` (THEN), `ands` (newline-joined extra `- **AND**` lines).
- `Spec` clusters are keyed `(project, capability)`. Sync merges delta
  requirements into them with the stock archive semantics: ADDED adds (implicit
  MODIFIED on name collision), MODIFIED replaces text and the entire scenario
  set, REMOVED deletes, RENAMED renames. A delta `purpose` only seeds a new Spec.
  A Spec is deleted (retired) only when the proposal declares
  `retireCapabilities: true` and the sync leaves it with zero requirements.
- Indices: `Proposal.id`, `Task.id`, `Spec.project` (create once, idempotent):
  `CREATE INDEX FOR (p:Proposal) ON (p.id)`.

## FalkorDB query rules (baked into the skills; learned from real failures)

1. **Parameters**: pass via the MCP `params` object with plain keys (no `$`
   prefix); reference as `$name` in the query.
2. **No `$map` inlining**: `CREATE (n $props)` fails - list properties
   explicitly: `CREATE (n {id: $id, name: $name})`.
3. **One mutation kind per query**: never mix `DETACH DELETE` with `MERGE` or
   `CREATE` in one query - FalkorDB mis-executes the combination (MERGE after a
   delete duplicates nodes instead of matching). Split into sequential queries.
4. **Strict WITH scoping**: any variable used after a `WITH` must be carried by
   it; final `RETURN`s must only reference in-scope variables.
5. **Empty UNWIND kills rows**: guard with
   `UNWIND (CASE WHEN size($list) > 0 THEN $list ELSE [null] END) AS x`.
6. **FOREACH variables don't escape**: use it for conditional `SET`/`CREATE`
   (`CASE WHEN cond THEN [1] ELSE [] END`), then re-`MATCH` nodes created inside.
7. **Reserved words**: `then` is unusable as a property; `when` needs backticks
   in property maps (`` `when` ``).
8. Deleted node ids get reused - never cache FalkorDB node ids across sessions
   (the renderer re-matches by name within a single query sequence).

## Renderer

`.zcode/scripts/openspec-graph-render.mjs` rebuilds the classic markdown tree
from the graph (format-faithful: rendered output passes `openspec validate`):

```
node .zcode/scripts/openspec-graph-render.mjs                 # active changes -> .zcode/export/
node .zcode/scripts/openspec-graph-render.mjs --change <name> # one change
node .zcode/scripts/openspec-graph-render.mjs --all           # include archived (changes/archive/<date>-<name>/)
node .zcode/scripts/openspec-graph-render.mjs --specs         # also render main specs
node .zcode/scripts/openspec-graph-render.mjs --list          # list changes, write nothing
node .zcode/scripts/openspec-graph-render.mjs --stdout        # print instead of writing
node .zcode/scripts/openspec-graph-render.mjs --out <dir>     # custom output root
node .zcode/scripts/openspec-graph-render.mjs --project <path> [--graph <name>]
```

Output layout mirrors the on-disk convention:
`changes/<name>/{proposal.md,design.md,tasks.md,specs/<capability>/spec.md,.openspec.yaml}`,
`changes/archive/<YYYY-MM-DD>-<name>/...`, and `specs/<capability>/spec.md`.
`- [x]` checkboxes come from `Task.status === 'completed'`.

The export directory is a **projection for humans** - the graph is the source of
truth. Never edit the export and expect it to flow back.

## Workflow ↔ skill mapping

| Skill | Graph operations |
| --- | --- |
| `openspec-propose` | one atomic query creates the whole cluster |
| `openspec-apply-change` | fetch cluster → implement code → flip `Task.status`, recompute `Proposal.status` |
| `openspec-update-change` | re-fetch cluster → confirmed edits via single-mutation queries |
| `openspec-explore` | read-only queries; capture = propose/update-style writes after confirmation |
| `openspec-sync-specs` | merge deltas into Spec clusters; set `specsSynced: true` |
| `openspec-archive-change` | verify zero pending Tasks → inline sync → `status: 'archived'` + `archiveName` |

The local `.bob/` mirrors use `/opsx-<name>` spellings instead of `/opsx:<name>`.
